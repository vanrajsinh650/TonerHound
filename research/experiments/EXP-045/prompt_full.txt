3. PHASE B — ALGORITHMIC RESEARCH AND SELECTION
=====================================================================

Based on the diagnostic breakdown, select and implement the appropriate algorithms. Do not implement all of them. Pick the two or three that match the dominant signals in your 200-sample audit.

ALGORITHM 1 — Row-Context Matching (for SUB_ROW_CONTEXT)

  The core idea: The correct occurrence is the one whose surrounding row cells match the surrounding extracted values of the target field.

  Build a row-level fingerprint for each candidate occurrence:
    - The target value's token string
    - The nearest sibling token to the left (if any)
    - The nearest sibling token to the right (if any)
    - The token directly above (same column)
    - The token directly below (same column)

  Score each candidate using a weighted similarity:
    score = w1 × similarity(target) + w2 × similarity(left) + w3 × similarity(right) + w4 × similarity(above) + w5 × similarity(below)

  Use a weighted dice coefficient or Jaccard similarity on character n-grams.

  Recommended weights (tune empirically):
    w1 = 1.0 (target value — must match)
    w2 = 0.5 (left sibling)
    w3 = 0.5 (right sibling)
    w4 = 0.3 (above)
    w5 = 0.3 (below)

  File: research/experiments/EXP-045/matching/row_context_matcher.py

ALGORITHM 2 — Column-Context Matching (for SUB_COLUMN_CONTEXT)

  The core idea: The correct occurrence is the one whose column header matches the expected schema field name.

  For each table, detect the header row using horizontal line density or font-weight analysis.
  For each candidate occurrence, find the header cell directly above it (same column).
  Score the header against the schema field name using token-set similarity.

  score = similarity(header_text, schema_field_name)

  Reject if score < 0.5.

  File: research/experiments/EXP-045/matching/column_context_matcher.py

ALGORITHM 3 — Global Row Assignment (for dense tables with many repeated values)

  The core idea: Instead of matching each field independently, solve the entire table's row assignment as a global optimization problem.

  This is the Hungarian algorithm applied at the row level, not the cell level.

  Build a cost matrix between:
    - Extracted records (schema rows)
    - Visual rows in the table (detected via line clustering)

  Cost between extracted record i and visual row j:
    cost(i, j) = 1 - (similarity of sibling values + similarity of row position + similarity of column alignment)

  Solve with scipy.optimize.linear_sum_assignment.

  This guarantees the globally optimal assignment for the entire table. No local greedy errors.

  File: research/experiments/EXP-045/matching/global_row_assigner.py

ALGORITHM 4 — Constraint Satisfaction Filter (for SUB_SECTION_CONTEXT and SUB_PAGE_POSITION)

  The core idea: Some disambiguation signals are hard constraints, not soft scores.

  Build a constraint graph:
    - Node = candidate occurrence
    - Edge = "these two candidates cannot both be correct" (mutual exclusivity)

  Apply hard constraints:
    - Only one candidate per extracted field
    - If two fields have the same gold value and they map to different schema paths, they must map to different occurrences
    - If a field is expected on page N, reject candidates on other pages

  Solve the constraint satisfaction problem using forward checking with backtracking.

  This is a small, tractable CSP. The number of candidates per field is typically < 20.

  File: research/experiments/EXP-045/matching/constraint_solver.py

ALGORITHM 5 — Optimal Transport for Fuzzy Candidate Matching (for SUB_REPETITION_PATTERN)

  The core idea: When the same value repeats N times, treat the candidate set as a distribution and find the optimal transport plan to the expected positions.

  This is a softer version of the Hungarian assignment. It allows partial matches and handles uncertainty gracefully.

  Use the Sinkhorn algorithm (fast approximation of OT) or the exact OT solver from POT (Python Optimal Transport).

  File: research/experiments/EXP-045/matching/optimal_transport_matcher.py

4. PHASE C — BUILD THE PIPELINE
=====================================================================

Build a gated pipeline. Each stage operates on fields the previous stage failed to resolve. Never override a passing field.

  STAGE 1: Column-context matcher
    Only applies to fields inside detected tables.
    Rejects when the header similarity is below threshold.

  STAGE 2: Row-context matcher
    Only applies when sibling tokens are available.
    Requires at least 2 of 5 sibling slots to be populated.

  STAGE 3: Global row assignment (Hungarian)
    Only applies to tables with ≥ 5 rows and ≥ 3 columns.
    Solves the entire table at once. No greedy.

  STAGE 4: Constraint satisfaction filter
    Only applies when multiple candidates survive Stages 1–3.
    Uses forward checking to prune the candidate space.

  STAGE 5: Optimal transport fallback
    Only applies when a field has > 5 candidate occurrences.
    Uses Sinkhorn to find the best soft match.

  STAGE 6: Preserve baseline
    If all stages fail, keep the baseline citation (the one that already scored IoU < 0.50).
