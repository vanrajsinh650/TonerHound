## 1. Executive Summary & Core Hypothesis

### The Problem
In EXP-011, structural evidence reranking achieved an 85% flip rate on curated ambiguous table arrays, lifting macro performance. However, EXP-012 revealed that downstream rerankers (both structural table rerankers and flat-form directional rerankers) are fundamentally bounded by candidate generator recall:
- If the true physical evidence box is absent or fragmented in the candidate generator's pool, no downstream reranker can select it.
- On flat forms and complex OCR documents, Candidate Recall@5 dropped as low as **36.73%** (vs 96.36% on tabular SEC filings), creating an unbridgeable ceiling.

### The Central Hypothesis
> **Hypothesis**: The primary performance ceiling on ExtractBench is **candidate generation, not candidate ranking**. Physical evidence is present in raw PDF text streams or OCR glyphs, but standard whitespace/token matching either omits it, splits it across non-contiguous tokens, or drops units (e.g., `%`, `$`).
> 
> By introducing a modular, extractor-independent **Candidate Recovery Engine** (`CandidateRecoveryEngine`) that targets the 5 primary failure classes during candidate generation, Candidate Recall@5 and Recall@1 will materially increase, unlocking downstream Word Grounding F1 without degrading precision or introducing template-specific hacks.

## 2. Priority Failure Classes & Technical Solutions

The modular [`CandidateRecoveryEngine`](file:///home/vanrajsinh/Projects/TonerHound/src/tonerhound/matching/candidate_recovery.py) addresses 5 priority failure classes identified during forensic analysis:

| Failure Class | Failure Pattern | Root Cause in PDF/OCR Stream | Recovery Mechanism | Example |
| :--- | :--- | :--- | :--- | :--- |
| **Class 1: Spaced-Token Numerics** | `3 3 . 3 3 3 3 %` | Digits, decimal points, and percent signs emitted as isolated 1-character tokens with small x-gaps. | Sliding window token concatenation with character-level whitespace elision and tight numeric parsing. | `3` `3` `.` `3` `3` `3` `3` `%` $\to$ `33.3333%` |
| **Class 2: OCR-Fragmented Numerics** | `-3` `186` or `21,` `693.` | Minus signs, currency symbols, or thousands commas split across adjacent OCR bounding boxes. | Adjacent token concatenation across punctuation boundaries; spatial unioning of bounding boxes. | `-3` + `186` $\to$ `-3186` |
| **Class 3: Split Percentage / Currency** | `33.3333333` ` %` | Number token and unit symbol separated by horizontal whitespace ($\le 0.035$ doc width). | Trailing/leading unit symbol absorption into the candidate span and bounding box union. | Token `33.3333333` absorbs adjacent `%` token box |
| **Class 4: Interleaved Sub-Row Values** | `TELCO 38 PARK EXPERTS AVENUE LLC` | Multi-line or two-column form cells where reading order interleaves two distinct rows into one line. | Fine-grained y-subband clustering ($|\Delta y| \le 0.006$) to extract contiguous sub-sequences. | `TELCO` `EXPERTS` `LLC` extracted from interleaved address line |
| **Class 5: Bounded Missing-Anchor Spans** | `Fruitland Park FL 34731` | OCR corruption or clipping removes one expected anchor token (e.g. `itland` instead of `Fruitland`). | Bounded substring / contiguous token-span matching with thresholded token overlap ($\ge 75\%$). | Recovers `itland Park FL 34731` when prefix is corrupted |

## 3. Architecture & Rules Compliance

### Implementation Overview
- **File**: [`src/tonerhound/matching/candidate_recovery.py`](file:///home/vanrajsinh/Projects/TonerHound/src/tonerhound/matching/candidate_recovery.py)
- **Integration**: Integrated seamlessly into [`EvidenceResolver.collect_candidates`](file:///home/vanrajsinh/Projects/TonerHound/src/tonerhound/resolution/resolver.py#L62-L154).
- **Execution Flow**:
  1. Standard matchers (exact, numeric, date, boolean) generate initial candidate pool.
  2. If exact candidate is absent, or to augment candidate depth, `CandidateRecoveryEngine.recover()` is invoked.
  3. Recovered candidates are tagged with descriptive `match_type` values (`recovered_spaced_numeric`, `recovered_fragmented_numeric`, `recovered_interleaved`, `recovered_bounded_span`).
  4. Deduplication is performed by spatial IoU ($\ge 0.70-0.85$) to prevent duplicate candidate clutter.
  5. Downstream `StructuralReranker` (EXP-011) and `FlatFormLabelReranker` (EXP-012) score and re-rank the recovered candidates alongside standard candidates.

## 6. Critical Diagnostics & Trigger Distribution

Every candidate recovered by `CandidateRecoveryEngine` records a structured diagnostic entry containing:
- `original_value`: Target extraction value
- `raw_document_tokens`: List of token strings in document order
- `reconstructed_candidate`: Assembled string
- `candidate_bbox`: Bounding box `[x, y, w, h]`
- `normalization_path`: Mechanism utilized
- `why_previously_missed`: Root cause analysis

### Trigger Distribution across Suites

| Recovery Mechanism | Description | Focused Cohort (34 Docs) | 32-Doc Gate Suite |
| :--- | :--- | :---: | :---: |
| `spaced_numeric` | Character-separated digits and punctuation | 1,962 | 2,254 |
| `ocr_fragmented_numeric` | Multi-token split values at minus/comma/decimal | 1,746 | 2,028 |
| `y_band_interleaved` | Sub-band reordering of multi-column cell tokens | 666 | 268 |
| `bounded_span` | Partial anchor loss in text stream | 224 | 178 |
| `split_percentage_currency` | Detached units ($`\%`$, $\$`$) | 2 | 80 |
| **Total Candidates Recovered** | | **4,600** | **4,808** |

### Representative Case Studies

#### Case Study A: Multi-Token Sub-Row Interleaving (`short/00581-2011-p0050`)
- **Field**: `partnership_name`
- **Target Value**: `"TELCO EXPERTS LLC"`
- **Document Tokens**: Raw tokens in visual line were ordered `["TELCO", "38", "PARK", "EXPERTS", "AVENUE", "LLC"]` because two table columns shared the same horizontal line.
- **Why Previously Missed**: Standard matcher required contiguous tokens in line order, failing to match across the street address tokens.
- **Recovery Path**: `y_band_interleaved` clustered tokens by exact y-subband ($y = 0.27263 \pm 0.004$) and reconstructed `["TELCO", "EXPERTS", "LLC"]` with bounding box `[0.08142, 0.27263, 0.19668, 0.00820]`.

#### Case Study B: Split Negative Sign (`short/07021-2016-p0026`)
- **Field**: `box_1_ordinary_business_income`
- **Target Value**: `-3186`
- **Document Tokens**: Raw tokens were emitted as `["-3", "186"]`.
- **Why Previously Missed**: Neither `"-3"` nor `"186"` matched `-3186`. Numeric parser rejected both in isolation.
- **Recovery Path**: `ocr_fragmented_numeric` concatenated adjacent tokens across the digit boundary within gap threshold $\le 0.035$, producing candidate `-3186` with merged bounding box `[0.6401, 0.1215, 0.0552, 0.0098]`.

#### Case Study C: Detached Percent Symbol (`medium/bar-lev-2022`)
- **Field**: `ending_capital_percentage`
- **Target Value**: `33.3333333`
- **Document Tokens**: `["33.3333333", "%"]` separated by a 0.012 coordinate gap.
- **Why Previously Missed**: Ground truth bounding box covered the percent sign; matching only `33.3333333` resulted in partial IoU (<0.50).
- **Recovery Path**: `split_percentage_currency` absorbed the trailing `%` token into the matched token span, achieving IoU > 0.85 with ground truth.
